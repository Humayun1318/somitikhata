# i18n.md

## 1. Library: next-intl

**Recommended: `next-intl`**, over `next-i18next` and `react-i18next`.

Why, specifically for this project and as of 2026:
- Built around the App Router and Server Components from the ground up — translations rendered in a Server Component add **zero bytes** to the client JavaScript bundle, which matters directly for the PWA/mobile-performance goals in `pwa.md` (most of this app's pages — dashboards, statements — are read-heavy and can be Server Components).
- Lighter than a full `next-i18next` stack (which pulls in `i18next` + `react-i18next` + `next-i18next` as three separate packages) — one dependency instead of three, for a project explicitly trying to stay junior-developer-maintainable.
- Native support for the `/en` / `/bn` locale-prefixed routing this project needs, with typed routing helpers.

`next-i18next` remains a reasonable choice if this were a Pages Router project or if a large existing i18next translation pipeline already existed — neither applies here.

## 2. Folder Structure

```
messages/
├── en.json
└── bn.json

app/
└── [locale]/
    └── ... (all routes, per architecture.md)

middleware.ts   # locale detection + redirect, combined with auth route protection
i18n/
├── request.ts   # next-intl server config
└── routing.ts   # defines locales: ['en', 'bn'], defaultLocale: 'bn'
```

**Default locale: `bn`.** The member base is Bangladeshi and the product's whole value proposition leans on being genuinely bilingual rather than "English app with a Bangla option" — defaulting to Bangla for an unrecognized visitor (with English one tap away) matches the actual audience better than defaulting to English and asking Bangla speakers to switch every time.

## 3. Translation File Organization

Flat namespaced JSON per locale, grouped by feature (not one giant flat file, and not one file per component — that granularity becomes unmanageable):

```json
// messages/en.json
{
  "common": { "save": "Save", "cancel": "Cancel", "loading": "Loading..." },
  "nav": { "dashboard": "Dashboard", "deposits": "Deposits", "loans": "Loans" },
  "auth": { "loginTitle": "Log in to your account", "registerTitle": "..." },
  "deposits": { "currentBalance": "Current Balance", "thisMonth": "This Month's Deposit" },
  "loans": { "activeLoan": "Active Loan", "remaining": "Remaining", "nextInstallment": "Next Installment" },
  "validation": { "required": "This field is required", "invalidPhone": "Enter a valid phone number" },
  "errors": { "generic": "Something went wrong. Please try again." }
}
```

`messages/bn.json` mirrors the exact same key structure. A missing key in one file is a build-time/dev-time warning from next-intl, not a silent blank string in production.

**No hardcoded UI text rule:** every user-facing string — including validation messages, empty states, toast confirmations, and button labels — goes through `useTranslations()` (client) or `getTranslations()` (server), never a literal string in JSX. This is enforced by convention now and can be enforced by an ESLint rule (`eslint-plugin-i18next` or similar) later if drift becomes a problem.

## 4. Language Switcher

A persistent control in the navbar (public pages) and in the app header (authenticated pages) — not buried in settings. Switching locale preserves the current route (`/en/dashboard` ↔ `/bn/dashboard`), not a reset to the homepage, and preserves any open form state where reasonably possible (locale switch is not expected to be a frequent mid-task action, but it shouldn't punish someone who does it).

## 5. SEO Implications

- Each locale gets its own indexable URL (`/en`, `/bn`), which is correct practice for genuinely bilingual content (as opposed to client-side-only text swapping, which search engines can't index separately per language).
- `hreflang` alternate tags on every public page, pointing `/en` and `/bn` versions at each other, plus an `x-default` pointing at `/bn` (the default locale) — this is what tells Google "these are the same page in two languages," preventing them from being seen as duplicate or unrelated content.
- Metadata (title, description, Open Graph) is defined per-locale in the translation files, not translated at request time — see `seo.md` for the full metadata approach.
- Only the `(public)` route group is relevant to SEO at all — `(auth)`, `(member)`, and `(admin)` route groups are `noindex` regardless of locale (see `seo.md`).

## 6. URL Strategy

`/en/...` and `/bn/...` prefixes on every route (via next-intl's `localePrefix: 'always'`), rather than a cookie-only locale with no URL distinction. Reasons specific to this project:
- Makes the bilingual landing page shareable/linkable in a specific language (a committee sharing the link with a Bangla-preferring member vs. an English-preferring one).
- Required for the `hreflang`/indexing approach above to work at all — a cookie-based locale switch is invisible to search engines.
- Costs nothing in complexity, since Next.js's routing already supports this as a first-class pattern via next-intl's middleware integration.
